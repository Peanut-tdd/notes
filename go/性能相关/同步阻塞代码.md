下面给你几个**真实、常见、而且很容易在高并发下拖慢 RT 的 Go 同步阻塞代码示例**



**一、最经典：`sync.Mutex`串行化请求**

```
var mu sync.Mutex
var counter int

func handler() {
    mu.Lock()
    defer mu.Unlock()

    counter++
    time.Sleep(10 * time.Millisecond) // 模拟业务
}
```

### 问题

- 所有请求 **串行执行**
- 并发越高，排队越长
- RT ≈ 请求排队时间 + 10ms





**二、共享连接 / 资源（最常见）**

全局 DB / Redis 连接池过小

```
var db *sql.DB

func query() {
    row := db.QueryRow("SELECT id FROM user WHERE id = ?", 1)
    var id int
    row.Scan(&id)
}
```

如果：

- 连接池 = 10
- 并发 = 10000

👉 **9990 个请求在等连接**







**三、`time.Sleep`/ 外部调用阻塞（同步 IO）**

模拟慢依赖

```
func handler() {
    resp, _ := http.Get("https://slow-api.example.com")
    io.ReadAll(resp.Body)
}
```

### 问题

- HTTP 客户端默认无超时
- 一个慢请求拖住 goroutine
- goroutine 越积越多





**四、channel 当成“锁”用（隐蔽但致命）**

```
ch := make(chan struct{}, 1)

func handler() {
    ch <- struct{}{}        // 阻塞
    defer func() { <-ch }()

    doSomething()
}
```

表面上是“限流”，实际上是：

- 所有请求排队
- 和 mutex 没本质区别



**五、Go 里「看起来并发，实际上同步」的典型写法**

```
func handler() {
    wg := sync.WaitGroup{}

    for _, task := range tasks {
        wg.Add(1)
        go func(t Task) {
            defer wg.Done()
            process(t)
        }(task)
    }

    wg.Wait() // ❌ 阻塞直到全部完成
}
```

### 问题

- handler 必须等所有 goroutine 结束
- RT = 最慢 task 的时间
- goroutine 爆炸
